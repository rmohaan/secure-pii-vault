# GCP configuration and deployment

This is a deployment guide/template, not an executed deployment. Choose the region, project, organization access policy and deployment runtime before provisioning. The application can run on Cloud Run with private VPC connectivity or on GKE with Workload Identity.

1. Enable Cloud KMS, Secret Manager and AlloyDB APIs. Create a runtime service account. Use an independently administered key project if required by your separation-of-duties policy.
2. Create four KMS keys in the approved region: field KEK, archive KEK, HMAC key and AlloyDB storage CMEK. The editable script configures a 90-day automatic rotation period on the three encryption keys and resource-scoped runtime grants. The HMAC key requires the planned application/data migration described in `design.md`; rotating it changes the searchable HMAC values.
3. Create an AlloyDB cluster using its CMEK configuration; assign the AlloyDB service agent access to the **storage CMEK only**. Create the primary instance and configure private network connectivity. Refer to [cluster creation](https://docs.cloud.google.com/alloydb/docs/cluster-create) and [CMEK setup](https://docs.cloud.google.com/alloydb/docs/use-cmek). Configure automated/continuous backups and their encryption keys explicitly.
4. Through an administrator connection, create the `investors` database, `investor_migrator`, `investor_app` and NOLOGIN `pii_auditor` roles, and schemas/grants equivalent to `infra/postgres/init.sh`. The Docker init script is local scaffolding; adapt database provisioning to your organization's managed AlloyDB administrator permissions. Grant CONNECT only to intended roles and remove public schema CREATE.
5. Run `src/main/resources/db/migration/V1__investors.sql` through your Flyway deployment job as `investor_migrator` with default schema `investor`. Flyway metadata should live in that schema. Never grant runtime schema ownership or supply the migration password to the production application.
6. Store the runtime database password as one Secret Manager secret version. Avoid passing credentials on CLI arguments or putting them in Terraform state unintentionally. Grant the runtime account accessor only on that secret. The application loads and CRC-checks it at startup through ADC.
7. Fill `.env.gcp.example` into your deployment environment. Direct database connections require `sslmode=verify-full` with a trusted CA and certificate-matching host. An AlloyDB Auth Proxy sidecar is an alternative; use its documented local connection configuration and keep that hop confined to the workload. This POC uses PostgreSQL JDBC, not an embedded AlloyDB connector.
8. Deploy the container with `SPRING_PROFILES_ACTIVE=gcp` and the attached runtime identity. The GCP profile uses JWT bearer tokens with issuer, audience, expiry and signature validation. Map approved IdP scopes to `investors.write`, `investors.read`, `investors.pii`. Do not activate both profiles.
9. Enable Cloud Audit Logs data-access events for KMS and Secret Manager and database auditing under your policy; export to protected log storage. Set ingress authentication/rate limits/body-size caps and alerts. Test an unauthorized user, denied archive decrypt, denied archive SELECT, KMS outage, corrupted envelope and restore before real data.

`infra/provision-keys.sh` is intentionally a one-time bootstrap template: review variables and run manually. Its `ROTATION_DAYS` default is 90. It does not create the cluster, secrets, networking, human grants or deployment. Key rotation and destruction must follow the runbook in `design.md`.
